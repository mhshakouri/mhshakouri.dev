# Arrowword Co-op: Aligned Spec (v2)

A cooperative web app for solving Persian arrowword puzzles together, from a photo, on two devices, without any OCR.

This document supersedes the original Supabase-based spec. It is the single source of truth for building the project as part of mhshakouri.dev. Decisions that changed are marked with "Changed:" so the history is visible.

Author preference: do not use the em dash character anywhere in code, comments, content, or commit messages for this project. Use commas, colons, or periods instead.

---

## 1. What this app is

Two people solve a Persian arrowword puzzle together. One person photographs a printed arrowword, marks the grid over the photo, and tags each cell by hand. Both people then open the puzzle via a shared link on their own devices, read clues by tapping clue cells (which zoom the relevant part of the photo), and fill in answer cells. Letters sync live over a WebSocket and persist, so progress is visible whether solving together or apart.

No OCR, no correctness checking, no puzzle generation. Humans read the clues. The app only knows the grid structure and holds the shared letters.

Changed: no accounts. A session link is the only credential (see section 5).

## 2. Placement and repos

Changed from standalone app to part of this site.

- UI lives in this repo at `src/app/playground/arrowword/` as client components. Pages remain fully prerendered shells; all dynamic behavior is client side, which keeps the Workers no-eval constraint irrelevant here.
- Sync backend is a separate small Cloudflare Worker in this repo under `workers/arrowword/` with its own `wrangler.jsonc`, deployed independently of the site worker. It owns one Durable Object class and one R2 bucket binding.
- The site page talks to the worker over HTTPS/WebSocket. CORS allows the site origin and localhost during development.

Rationale for a separate worker: the site worker is generated by OpenNext and redeployed on every content push. The game backend should not churn with blog posts, and coupling DO migrations to site deploys invites mistakes.

## 3. Cell taxonomy (unchanged)

Every grid cell is exactly one of four types:

1. Dead: not interactive.
2. Clue: not typeable. Tapping opens a zoomed view of that cell from the photo.
3. Answer: fillable, one letter, shared and synced.
4. Prefilled: shows a given letter from the puzzle. Locked in v1.

Only answer cells produce mutable state.

## 4. Data model

Changed: Puzzle, Game, and cell_values collapse into one Session document owned by one Durable Object. "Re-solve the same puzzle" is out of scope; a clone-session feature can come later.

```ts
export type CellType = "dead" | "clue" | "answer" | "prefilled";

export interface Cell {
  type: CellType;
  letter?: string; // only when type === "prefilled", single grapheme
}

export interface Point {
  x: number; // normalized 0..1 in image space
  y: number;
}

export interface GridAlignment {
  topLeft: Point;
  topRight: Point;
  bottomRight: Point;
  bottomLeft: Point;
}

export interface SessionDoc {
  v: 1;
  title: string;
  photoKey: string; // R2 object key
  rows: number;
  cols: number;
  alignment: GridAlignment;
  cells: Cell[][]; // row-major
  // key is "row,col"; value is the letter plus a timestamp for LWW display
  letters: Record<string, { ch: string; at: number }>;
  createdAt: number;
}
```

Never write player input into `cells`. Player letters go only into `letters`. Prefilled cells never get `letters` entries.

## 5. Sessions and sharing (replaces Auth)

Changed: capability links instead of Supabase magic-link auth.

- Creating a session returns an unguessable id (128 bits, base58 or hex from `crypto.getRandomValues`).
- The share link is `/playground/arrowword/s/[id]`. Whoever has the link is a player. There are no roles: creator and partner have identical rights after setup.
- Consequence to accept: anyone holding the link can edit. For a private two-person tool this is the feature, not a bug. Do not add auth complexity to v1.
- The landing page at `/playground/arrowword` lists sessions the browser has visited (localStorage) and offers "new puzzle".

## 6. Tech stack

Changed throughout.

- UI: this site's existing stack. Next.js 16 App Router, TypeScript strict, Tailwind v4 tokens. Client components for everything interactive.
- Sync and storage: one Cloudflare Worker with a Durable Object class (`ArrowwordSession`, one instance per session, SQLite-backed storage) and an R2 bucket (`arrowword-photos`) for photos.
- Use the WebSocket Hibernation API in the DO so idle open tabs cost nothing.
- No Supabase, no Postgres, no auth service, no Vercel.

Cost reality: at two-user scale everything fits in Cloudflare free tiers.

## 7. Worker API

Small and boring on purpose.

- `POST /session` creates a session: stores an empty SessionDoc, returns `{ id }`.
- `PUT /session/:id/photo` uploads the (client-downscaled) JPEG to R2 as `photos/:id.jpg`, sets `photoKey`.
- `GET /session/:id/photo` streams the photo from R2 (long cache headers; the photo never changes after setup).
- `PUT /session/:id/puzzle` writes the fixed puzzle fields (title, rows, cols, alignment, cells). Allowed only once, during setup.
- `GET /session/:id/ws` upgrades to WebSocket.

WebSocket protocol (JSON messages):

- server -> client on connect: `{ type: "state", doc: SessionDoc }`
- client -> server: `{ type: "set", row, col, ch }` or `{ type: "clear", row, col }`
- server -> all clients: `{ type: "cell", row, col, ch | null, at }`
- server -> all clients on join/leave: `{ type: "peers", count }` (cheap presence)

Conflict handling: the DO is single-threaded, so writes serialize naturally. Last write wins per cell. Timestamps exist for potential "who filled what" display later, not for merging.

Client resilience: optimistic local echo on type, reconnect with fresh `state` on socket drop, retry the last unacknowledged write.

## 8. Grid to image alignment (unchanged)

Four draggable corner handles on the photo produce a `GridAlignment` of normalized points. Cell quadrilaterals come from bilinear interpolation (`quadPoint(a, u, v)` exactly as in the original spec, kept in `lib/alignment.ts` under the arrowword folder). Flat-photo assumption is fine for v1; perspective transform is a later upgrade.

Clue zoom: render the full photo in a fixed viewport and use CSS transform (scale plus translate) so the cell rectangle fills the viewport, clipped by overflow hidden. No canvas.

Photo handling: downscale client side before upload (canvas, longest edge 2000px, JPEG quality ~0.8). Validate clue legibility at this size early with a real photo, since zoom quality depends on it.

## 9. Script and direction (simplified after review, 2026-07-06)

Changed: RTL is a non-issue for v1, by design. The app has no concept of words: word boundaries and reading direction live in the photo and in the players' heads. Cells are absolutely positioned quads in image space, and CSS direction has no effect on absolutely positioned elements.

- Coordinates are purely spatial: col 0 is the leftmost column in the image, always. Direction never renumbers the grid. (The original spec's "col 0 is the visual right edge" note is retired.)
- No auto-advance in v1: tap a cell, type one letter. Without run detection the app cannot know if a cell belongs to a horizontal or vertical word anyway. Run detection plus direction-aware advance (leftward for horizontal Persian answers) is a v2 feature, and that is the only place direction will ever enter the code.
- A single grapheme per cell renders in isolated letter form, which matches how printed Persian crosswords display letters. No bidi handling, no shaping logic.

What survives, and neither item is about direction:

- Grapheme discipline, still the risk center: one keypress maps to one cell. Use a hidden input to capture keystrokes, `Intl.Segmenter` to enforce single graphemes, and test ZWNJ and connected-form behavior on real Android and iOS Persian keyboards early.
- Font coverage: the site's Geist fonts have no Arabic-script glyphs. Use a system fallback stack for answer letters in v1; adopt Vazirmatn later only if the fallback renders poorly.

## 10. Setup flow (unchanged in spirit)

Route: `/playground/arrowword/new`. Client wizard:

1. Photo: pick or take, downscale, `POST /session` then `PUT photo`.
2. Grid size: rows and cols.
3. Align: drag four corners, live overlay of computed cell lines.
4. Tag: tap cells to cycle type; prompt for prefilled letters. Legend visible.
5. Save: `PUT puzzle`, show the share link prominently (copy button), go to play.

Acceptance: photo to saved, tagged, aligned puzzle entirely by hand, then a working share link.

## 11. Play flow (unchanged in spirit)

Route: `/playground/arrowword/s/[id]`.

1. Connect WebSocket, receive `state`, render grid over photo, responsive.
2. Dead inert; clue zooms; answer selects and types (set/clear over WS with optimistic echo); prefilled locked.
3. Apply incoming `cell` messages. Show a subtle peer indicator from `peers`.

Acceptance: two devices on the same link fill cells and see each other's letters live; letters survive both closing and reopening.

## 12. Milestones

- A0 Worker skeleton: DO + R2 + all endpoints, deployed; `/playground` index page and arrowword landing exist. Acceptance: curl can create a session, upload a photo, set a puzzle, and two websocat clients see each other's set messages.
- A1 Photo and alignment UI: upload, downscale, rows/cols, corner drag, overlay. Acceptance: overlay lines match a real printed grid.
- A2 Tagging and save: tap to tag, prefilled letters, save, share link. Acceptance: a fully tagged puzzle persists and reloads via its link.
- A3 Play rendering: grid over photo, four cell types visually distinct, clue zoom, Persian letters render correctly in cells. Acceptance: looks right on phone and desktop, clues readable.
- A4 Sync: typing syncs both ways with reconnect handling. Acceptance: the two-device test passes.
- A5 Polish: Persian keyboard hardening, loading/empty/error states, peer indicator, copy-link UX.

Out of v1 (unchanged): OCR, auto grid detection, perspective correction, correctness checking, generation, roles/auth, per-player colors.

## 14. Open questions (non-blocking)

- Crop-and-cache clue images vs transform-on-the-fly: start with transform, revisit only if zoom feels slow on phones.
- Who-filled-what color coding: timestamps and a per-device id would suffice; decide after real use.
- Session expiry: R2 and DO storage are cheap enough to keep sessions forever in v1; add cleanup only if it ever matters.
